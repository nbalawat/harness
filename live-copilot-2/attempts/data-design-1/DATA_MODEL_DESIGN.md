# Data Model Design

## Overview
This data model captures the core entities required to support a support-team assistant application where:
- Analysts interact with an AI assistant through conversational chat
- The assistant provides draft answers grounded in the organization's product knowledge
- Analysts must explicitly approve drafts before they can be sent
- All conversations and decisions are audited for quality review

## Tables

### 1. `conversations`
Represents a distinct conversation thread between an analyst and the system.

**Addresses:** REQ-004 (persist conversation history), REQ-006 (list/search past conversations)

**Purpose:**
- Store top-level conversation metadata
- Enable analysts to list, search, and reopen past conversations (REQ-006)
- Provide conversation grouping for messages and approvals

**Columns:**
- `id`: Unique identifier (UUID or similar)
- `created_at`: Timestamp when conversation was initiated
- `updated_at`: Timestamp of last activity in conversation
- `subject`: Optional title/summary of the conversation topic

---

### 2. `messages`
Represents individual turns in a conversation: one analyst question + one assistant draft per message.

**Addresses:** REQ-002 (chat interface with turn-by-turn history), REQ-004 (persist conversation history), REQ-005 (capture question, draft, timestamps)

**Purpose:**
- Store the complete record of each turn in the conversation
- Preserve analyst questions and assistant drafts as they were generated
- Support conversation history display and review
- Enable quality assessment with question/draft/timestamp triad (REQ-005)

**Columns:**
- `id`: Unique identifier for this message/turn
- `conversation_id`: Foreign key to `conversations`
- `sequence`: Order of this turn within the conversation (1-indexed)
- `role`: Indicates who/what generated each entry (e.g., "analyst", "assistant")
- `analyst_question`: The question posed by the analyst
- `assistant_draft`: The initial draft response generated by the assistant
- `created_at`: Timestamp when the message was created

**Note:** The draft stored here is the *unapproved* version. Once approved (and possibly edited), the approved version is stored in the `approvals` table.

---

### 3. `approvals`
Represents the analyst's decision on an assistant draft: approve, edit-then-approve, or reject.

**Addresses:** REQ-009 (explicit approval required), REQ-012 (approve-as-is, edit-then-approve, reject), REQ-013 (audit trail: who, when, edited?)

**Purpose:**
- Enforce that no unapproved draft leaves the application
- Record which analyst approved/rejected and when
- Track whether the draft was edited before approval
- Support audit trails and quality reviews
- Preserve the final approved text (if edited)

**Columns:**
- `id`: Unique identifier for this approval event
- `message_id`: Foreign key to `messages`
- `decision`: Enumeration of approval status (e.g., "approved", "rejected")
- `analyst_id`: Identifier of the analyst who made the decision (can be nullable/optional if REQ-019 chooses unauthenticated mode)
- `edited_draft`: The edited text if the analyst modified the draft before approving (nullable if not edited)
- `was_edited`: Boolean flag indicating whether `edited_draft` differs from the original assistant draft
- `approved_at`: Timestamp when the approval decision was made

**Note:** The separation of `edited_draft` and `was_edited` allows the system to:
1. Know whether edits were made (boolean flag for UI/audit)
2. Store what the edits were (for quality review and history)
3. Distinguish "not edited" from "edited but identical" if needed

---

### 4. `citations`
Stores the source passages and references that grounded each assistant draft.

**Addresses:** REQ-011 (answers cite sources, citations shown to analyst and stored for verification)

**Purpose:**
- Preserve the knowledge corpus passages used to generate each answer
- Enable reviewers to verify that answers were actually grounded in product knowledge (not hallucinated)
- Support transparency: show analysts which sources informed the draft
- Maintain audit trail of what knowledge was available at the time the answer was drafted

**Columns:**
- `id`: Unique identifier for this citation
- `message_id`: Foreign key to `messages`
- `source_title`: Title or name of the source document/page
- `source_passage`: The actual text passage from the knowledge corpus that was used
- `source_url`: Optional URL or identifier for deeper navigation to the source

**Note:** Multiple citations per message are supported (1:N relationship with `messages`). If a message has no citations, it represents either:
1. A rejection decision (no draft was approved to need citations)
2. An answer that was entirely edited by the analyst
3. An unexpected state that should be caught in quality review

## Requirement Coverage

✓ **REQ-002**: Chat interface with turn-by-turn history
  → `messages` table stores each turn; `conversations` provides thread grouping

✓ **REQ-004**: Conversation history persisted beyond session and reviewable afterwards
  → `conversations` and `messages` enable this; `updated_at` supports "recent" queries

✓ **REQ-005**: Stored record captures question, draft answer, approval, timestamps
  → `messages` stores question, draft, and created_at; `approvals` stores decision and approved_at

✓ **REQ-006**: List, open, search past conversations; reuse previous answers
  → `conversations.subject`, `updated_at`, and full message history enable search and retrieval; approved drafts in `approvals.edited_draft` (or original in `messages.assistant_draft` if not edited) can be reused

✓ **REQ-009**: Explicit approval required; impossible for unapproved draft to leave
  → `approvals` table is the gate: no approval record = no sending; application enforces this in logic

✓ **REQ-011**: Answers cite sources; citations shown and stored for verification
  → `citations` table links each message to its source passages; allows verification and transparency

✓ **REQ-012**: Approve-as-is, edit-then-approve, reject
  → `approvals.decision` and `was_edited` flag support all three paths; `edited_draft` stores final text if edited

✓ **REQ-013**: Approval audit trail: who, when, edited?
  → `approvals.analyst_id`, `approved_at`, and `was_edited` capture all audit requirements

## Not Modeled

**REQ-001, REQ-008** (Functional/process logic): Not data model concerns; they describe the workflow, not what gets stored.

**REQ-014** (Retention policy): "Indefinite retention, no auto-purge" is an operational/governance rule, not a data model concern. The schema supports it (no soft-delete or TTL columns).

**REQ-017** (Knowledge corpus ingestion): Marked "unknown confidence"; the mechanism for how product knowledge is supplied and indexed is outside the scope of this data model. The system uses an indexed corpus at runtime; storing the corpus metadata/provenance is not specified in requirements.

**REQ-018** (Delivery mechanism): Marked "unknown confidence"; whether the app sends replies or hands them off to analysts is a delivery choice, not a data model concern. The approved reply is available in `approvals.edited_draft` (or `messages.assistant_draft` if unchanged).

## Design Decisions

1. **No separate "draft" and "final" tables**: Drafts and approvals coexist in `messages` and `approvals`. An approval row signals that a message's draft has been reviewed; the `edited_draft` column in `approvals` preserves any modifications.

2. **Optional `analyst_id`**: Allows for two deployment scenarios:
   - Authenticated multi-analyst: `analyst_id` is populated and enables per-person audit trail (addresses REQ-013)
   - Unauthenticated single-team: `analyst_id` can be null or a constant identifier

3. **Multiple citations per message**: The 1:N relationship in `citations` allows one message to cite multiple source passages, supporting answers that synthesize from multiple documents.

4. **Immutable message record**: Once a message is created, `messages.analyst_question` and `messages.assistant_draft` are never modified. This preserves audit integrity. The analyst's edits go into `approvals.edited_draft`, creating a clean audit trail: "original draft → edits → final approved text".

5. **No soft-delete or retention fields**: Supports the indefinite-retention model (REQ-014). Deletion, if implemented, can be a physical removal; the schema doesn't enforce time-based purging.

6. **Flat approval structure**: One approval per message (1:1). Rejection doesn't create an approval record (or stores `decision='rejected'`). A subsequent regenerated draft would be a new message with its own approval.

## Future Considerations (Out of Scope for v1)

- **Knowledge corpus metadata**: If REQ-017 is clarified to require storing corpus versions, indexes, or sync status, add a `documents` or `knowledge_versions` table.
- **External delivery tracking**: If REQ-018 chooses email/ticketing integration, add an `outbound_messages` or `delivery_events` table to track what was sent to the customer.
- **Multi-tenancy**: REQ-016 explicitly excludes this from v1; if needed in v2, add `team_id` or `organization_id` to `conversations`, `approvals`, etc.
- **User accounts**: If REQ-019 chooses SSO/per-analyst accounts, add an `analysts` table and strengthen the foreign key on `approvals.analyst_id`.
