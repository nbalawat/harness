# KYC Review Desk — slices

- **Slice 1 — Case intake and deterministic completeness check** (`case-intake-completeness`; REQ-001…REQ-014, REQ-055, REQ-070, REQ-089, REQ-094). A submission opens a case and runs the approved `case-intake-and-risk-scoring` workflow through `workflow_engine` — handlers `open_case_from_submission`, `run_document_completeness_check`, `mark_case_ready`, `compute_risk_score_from_matrix`, `start_sla_clock` and `return_case_with_missing_documents` are registered at import in `backend/ext_cases.py`. The package is checked mechanically against versioned Document Checklist v2.0 (`backend/kyc_policy.py`), including conditional items for deep ownership chains, regulated industries and expected cross-border activity: a complete package moves the case to `ready` with a case-ready timestamp, an incomplete one is `returned` with the itemised `missing_documents` list plus a notification to the submitter. No role may waive a required item — `POST /cases/{ref}/waive-document` always refuses with 403 and records the refusal on the trail. Cases are addressed case-insensitively by submission reference. Endpoints, all registered outside `/api/` so the `/api/{table}` catch-all cannot shadow them: `GET /checklist`, `POST /cases`, `GET /cases`, `GET /cases/{reference}`, `POST /cases/{reference}/waive-document`. Storage is `db.store` only (`cases`, `case_cycles`, `documents`, `missing_documents`, `notifications`, `audit_trail`, `risk_scores`, `sla_tracking`, `users`); every state change writes an `audit_trail` row via `ext_audit.record`. UI: a live intake form and register table added inside the design's existing `#screen-worklist`, and a live case file showing the mechanical completeness result and outstanding-item list inside `#screen-case` — both built from the Dossier design's own classes and `tokens.css` variables, `textContent` only, with `cases.js` added alongside the untouched `app.js`. One reference is one case for the life of the relationship: re-submitting an existing reference opens a new **cycle** on the same `case_id` (`cases.cycle`, checklist and missing-document rows stamped with the cycle they belong to), matching the chosen design's "Returned register — outstanding at the RETURNED cycle / Cycles 2" reading of a case file. Each cycle gets its own immutable snapshot row in the new `case_cycles` table (package, attributes, risk factors, the three policy versions that applied, and the cycle's outcome — status, missing documents, score and band), so a later cycle never retroactively rewrites an earlier one (REQ-070) and `GET /cases/{ref}` returns the full `cycles` history. `documents`, `missing_documents`, `risk_scores` and `sla_tracking` rows all carry their `cycle`. A new cycle clears the previous cycle's score, band, approver and SLA clock, so a case whose latest cycle is RETURNED never advertises a stale band or a live due date; `sla_breached` is deliberately *not* cleared, because a recorded breach is permanent (REQ-053). Prior decision records are never rewritten by a resubmission; the resubmission itself is an audited event (`case_resubmitted`, old and new status, named submitter). **Recorded deviation from `artifacts/data-design/data_model.json`** (this step cannot edit that artifact, so this note is the only trace a regeneration has to work from — please fold it back in). `backend/models.py` was extended with: (1) new table **`case_cycles`** (per-cycle snapshot, columns listed in `models.py`); (2) new column **`cycle`** on `cases`, `documents`, `missing_documents`, `risk_scores`, `sla_tracking`, `assessment_memos` and `approvals`; (3) the domain columns `cases` actually carries (`case_reference`, `client_reference`, `client_name_normalized`, `entity_type`, `submitted_by`, `returned_at`, `total_risk_score`, `risk_band`, `required_approver_role`, `sla_start_timestamp`, `sla_due_timestamp`, `sla_hours`) — without these `ext_export.py`'s TABLES-driven CSV writer silently drops them from slice 6's export; (4) decision columns on `case_cycles` (`decision`, `decided_at`, `decided_by_user_id`, `decided_by_role`) for slice 4 to stamp; (5) the chat-shell/seed-data table **`conversations`**, which the pre-existing `test_table_crud` requires (the suite was red before this slice).

  **Policy provenance.** `kyc_policy.py` transcribes the ingested corpus verbatim, not values fitted to the acceptance numbers: Risk Rating Matrix v2.1 weights (jurisdiction .30, entity structure .25, industry .20, sanctions .15, expected activity .10) and 0-100 scales, with an explicit "otherwise" default per factor; Document Checklist v2.0 including the *depth > 1* structure-chart trigger; Escalation and SLA Policy v1.4 including the full three-step chain Compliance Officer → Head of Financial Crime → COO (`kim.coo`). The matrix reproduces the slice-plan totals (55 / 51 / 76) because it is the bank's matrix, and it scores every other input correctly too.

  **Notes for later slices.** (a) *Band casing* — bands are stored and served lowercase (`"high"`), which slice 2's acceptance requires; but `workflows.json`'s `high_risk_escalation_gate` compares `evaluate_sla.risk_band` to the literal `"High"`, so slice 5's `evaluate_case_sla_status` handler must emit `kyc_policy.band_label(band)` into workflow context while still persisting lowercase. (b) *Handler ownership* — `workflow_engine.register_handler` is last-writer-wins across the sorted `ext_*.py` import order; slice 1 owns `compute_risk_score_from_matrix` and `start_sla_clock` (both real, matrix v2.1 and the business-hour clock), so slices 2 and 5 should extend `ext_cases.py`/`kyc_policy.py` rather than re-register them from a new module. (c) *Identity* — `ext_cases.acting_user(authorization, claimed)` prefers `ext_auth.current_user`; slice 4 must enforce tiers through `rbac` (kept in sync from the `users` table by `ext_cases.sync_rbac()`), never from the request body alone. (d) *Memo version numbering (slice 3 — read this first)* — number `assessment_memos.version` **per (`case_id`, `cycle`)**, starting at 1 for each cycle, and write the `cycle` column. Slice 3's acceptance asserts version 1 then version 2 for `ACC-HIGH-001`; on a cumulative second run in one process slice 2 re-POSTs that reference first, so the case is at cycle 2 and naive per-case numbering would yield 3 and 4 and fail every memo check. (e) *Decision idempotency* — slice 4's "second decision on the same case → 409" must key off **an existing `approvals` row for (`case_id`, `cycle`)**, not off `cases.status`. Intake deliberately stays permissive: a resubmission reopens a decided case as a new cycle rather than returning an error, because refusing it would break a cumulative acceptance re-run in a single process (slice 2 re-POSTs `ACC-HIGH-001` after slice 4 has approved it). Keying on (case_id, cycle) gives the right answer in both a single run and a repeated one. (f) *Decisions must stamp the cycle* — slice 4 must call `ext_cases.stamp_cycle(case_id, decision=…, decided_at=…, decided_by_user_id=…, decided_by_role=…)` when it records a decision; the `case_cycles` snapshot carries those columns and slice 6's `/cases/{ref}/reproduction` reads them, so without the call a decided-then-resubmitted cycle reproduces with a stale `"ready"`/`"returned"` outcome. (g) *Score/SLA on resubmission* — the score and SLA fields are cleared at the start of every cycle and only rewritten on the complete path, so slice 5's evaluator must skip cases with no `sla_due_timestamp` rather than assume one exists.
