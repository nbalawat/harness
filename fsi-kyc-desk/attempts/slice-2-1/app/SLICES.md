# KYC Review Desk — slices

- **Slice 1 — Case intake and deterministic completeness check** (`case-intake-completeness`; REQ-001…REQ-014, REQ-055, REQ-070, REQ-089, REQ-094). A submission opens a case and runs the approved `case-intake-and-risk-scoring` workflow through `workflow_engine` — handlers `open_case_from_submission`, `run_document_completeness_check`, `mark_case_ready`, `compute_risk_score_from_matrix`, `start_sla_clock` and `return_case_with_missing_documents` are registered at import in `backend/ext_cases.py`. The package is checked mechanically against versioned Document Checklist v2.0 (`backend/kyc_policy.py`), including conditional items for deep ownership chains, regulated industries and expected cross-border activity: a complete package moves the case to `ready` with a case-ready timestamp, an incomplete one is `returned` with the itemised `missing_documents` list plus a notification to the submitter. No role may waive a required item — `POST /cases/{ref}/waive-document` always refuses with 403 and records the refusal on the trail. Cases are addressed case-insensitively by submission reference. Endpoints, all registered outside `/api/` so the `/api/{table}` catch-all cannot shadow them: `GET /checklist`, `POST /cases`, `GET /cases`, `GET /cases/{reference}`, `POST /cases/{reference}/waive-document`. Storage is `db.store` only (`cases`, `case_cycles`, `documents`, `missing_documents`, `notifications`, `audit_trail`, `risk_scores`, `sla_tracking`, `users`); every state change writes an `audit_trail` row via `ext_audit.record`. UI: a live intake form and register table added inside the design's existing `#screen-worklist`, and a live case file showing the mechanical completeness result and outstanding-item list inside `#screen-case` — both built from the Dossier design's own classes and `tokens.css` variables, `textContent` only, with `cases.js` added alongside the untouched `app.js`. One reference is one case for the life of the relationship: re-submitting an existing reference opens a new **cycle** on the same `case_id` (`cases.cycle`, checklist and missing-document rows stamped with the cycle they belong to), matching the chosen design's "Returned register — outstanding at the RETURNED cycle / Cycles 2" reading of a case file. Each cycle gets its own immutable snapshot row in the new `case_cycles` table (package, attributes, risk factors, the three policy versions that applied, and the cycle's outcome — status, missing documents, score and band), so a later cycle never retroactively rewrites an earlier one (REQ-070) and `GET /cases/{ref}` returns the full `cycles` history. `documents`, `missing_documents`, `risk_scores` and `sla_tracking` rows all carry their `cycle`. A new cycle clears the previous cycle's score, band, approver and SLA clock, so a case whose latest cycle is RETURNED never advertises a stale band or a live due date; `sla_breached` is deliberately *not* cleared, because a recorded breach is permanent (REQ-053). Prior decision records are never rewritten by a resubmission; the resubmission itself is an audited event (`case_resubmitted`, old and new status, named submitter). **Recorded deviation from `artifacts/data-design/data_model.json`** (this step cannot edit that artifact, so this note is the only trace a regeneration has to work from — please fold it back in). `backend/models.py` was extended with: (1) new table **`case_cycles`** (per-cycle snapshot, columns listed in `models.py`); (2) new column **`cycle`** on `cases`, `documents`, `missing_documents`, `risk_scores`, `sla_tracking`, `assessment_memos` and `approvals`; (3) the domain columns `cases` actually carries (`case_reference`, `client_reference`, `client_name_normalized`, `entity_type`, `submitted_by`, `returned_at`, `total_risk_score`, `risk_band`, `required_approver_role`, `sla_start_timestamp`, `sla_due_timestamp`, `sla_hours`) — without these `ext_export.py`'s TABLES-driven CSV writer silently drops them from slice 6's export; (4) decision columns on `case_cycles` (`decision`, `decided_at`, `decided_by_user_id`, `decided_by_role`) for slice 4 to stamp; (5) the chat-shell/seed-data table **`conversations`**, which the pre-existing `test_table_crud` requires (the suite was red before this slice); (6) the columns `cases` carries for the submitted package itself — **`submitted_documents`**, **`attributes`**, **`risk_factors`** — and on `risk_scores` the working of the calculation — **`factor_weights`**, **`factor_contributions`**, **`factor_breakdown`**, **`risk_matrix_version`**. These are written by intake and were previously undeclared, so `ext_export.py`'s `csv.DictWriter(..., extrasaction="ignore")` would have silently dropped every one of them from slice 6's export and from any other TABLES-driven consumer.

  **Corrections made in this pass (review findings).** (i) *nginx prefix shadowing* — `frontend/nginx.conf` proxied `location /cases`, which is an nginx **prefix** match and therefore also swallowed `GET /cases.js`, proxying the slice's own script to the backend (which serves no static files) and killing the entire slice-1 UI under `docker-compose`. The dev server mounts StaticFiles and so never showed it. Now `location = /cases` + `location /cases/` (same for `/checklist` and `/audit`), leaving `/cases.js` to be served as the static asset it is. (ii) *rbac self-grant* — `sync_rbac()` fed every `users` row into `rbac`, and `users` is in `models.TABLES`, so the generic `POST /api/{table}` catch-all let anyone insert `{"username":"mallory","role":"compliance_officer"}` and self-grant the tier that slice 4 enforces with `rbac.require`. Grants are now filtered to the approved roster in `kyc_policy.SEED_USERS`, and `role_of()` likewise refuses to read a role off a row that is not on the roster, so a spoofed account cannot dignify itself in the audit trail either. **A new decision-maker is added to `kyc_policy.SEED_USERS`, never by posting a row.** (iii) *audit roles* — `audit()` previously fell back to `"system"` for any actor with no roster role, which conflated a human claim with the deterministic workflow steps; the machine actors (`completeness-check`, `risk-matrix-engine`, `sla-evaluator`) are now named explicitly and an off-roster human is recorded `"unroled"`, keeping REQ-089's "who did it" answerable. (iv) *nginx prefix matches* — `/chat` and `/agents` were pre-emptively narrowed to exact matches too, so a later slice shipping `frontend/chat.js` or `frontend/agents.js` does not hit the same shadowing bug. (v) *design control* — `frontend/app.js` wrote `textContent` onto `#agent-mode`, which in this design is a `<select>`; that deleted its four `<option>` children and rendered the approved design's operating-mode control empty on every load. It now writes "what is answering" into the design's own sibling `.agentmode__note` whenever the target element has children, preserving both the control and the transparency the block exists for. (vi-b) *identity hardening* — a caller may no longer claim to BE a deterministic workflow step (`completeness-check`, `risk-matrix-engine`, `sla-evaluator`); `acting_user()` rejects those names with 400 on the **resolved** identity — session user and body claim alike, because `ext_auth.login` issues a token for any username, so guarding only the claim would let a caller simply log in as `sla-evaluator`. `acting_user()` also canonicalises through `canonical_username()`, so one person's actions cannot split across `Ana.Analyst`/`ana.analyst` on the trail and the name written there is the exact string `rbac` grants under. **Slice 4: `rbac` looks up by exact string, so call `ext_cases.canonical_username(name)` before `rbac.require(...)`** — without it "Cora.Compliance" reads as `compliance_officer` on the trail while `rbac.require` refuses it. (vi-c) *`db.store` in-place mutation* — slice 1's status/score/SLA/cycle writes mutate the dicts `store.list()` returns, which is the certified scaffold's own idiom (`approval_flow.py` does the same) and works because `db.py` is in-memory. `sqlite_store.py` ships in-tree but is imported nowhere. **Whoever lands the durable adapter must add `Store.update()` and convert those six call sites, or every slice-1 state transition becomes a silent no-op while the audit rows still claim it happened.** **(vi) Warning for slice 4 — `POST /auth/login` in the scaffold's `ext_auth.py` issues a session token for ANY username with no credential check.** Slice 1 grants `compliance_officer` to the literal name `cora.compliance`, so tier enforcement built only on `rbac.require(current_user(...), role)` (note (c)) is bypassable by logging in as that name. Slice 4 must address this where it enforces the tier; slice 1 cannot fix `ext_auth.py` without exceeding its scope. (vii) *acceptance regression guard* — `backend/tests/test_slice1_cases.py` now replays the slice plan's seven acceptance checks verbatim (`test_slice_plan_acceptance_checks_pass_in_order`), so a regression fails in the suite instead of costing a boot cycle.

  **Policy provenance.** `kyc_policy.py` transcribes the ingested corpus verbatim, not values fitted to the acceptance numbers: Risk Rating Matrix v2.1 weights (jurisdiction .30, entity structure .25, industry .20, sanctions .15, expected activity .10) and 0-100 scales, with an explicit "otherwise" default per factor; Document Checklist v2.0 including the *depth > 1* structure-chart trigger; Escalation and SLA Policy v1.4 including the full three-step chain Compliance Officer → Head of Financial Crime → COO (`kim.coo`). The matrix reproduces the slice-plan totals (55 / 51 / 76) because it is the bank's matrix, and it scores every other input correctly too.

  **Notes for later slices.** (a) *Band casing* — bands are stored and served lowercase (`"high"`), which slice 2's acceptance requires; but `workflows.json`'s `high_risk_escalation_gate` compares `evaluate_sla.risk_band` to the literal `"High"`, so slice 5's `evaluate_case_sla_status` handler must emit `kyc_policy.band_label(band)` into workflow context while still persisting lowercase. (b) *Handler ownership* — `workflow_engine.register_handler` is last-writer-wins across the sorted `ext_*.py` import order; slice 1 owns `compute_risk_score_from_matrix` and `start_sla_clock` (both real, matrix v2.1 and the business-hour clock), so slices 2 and 5 should extend `ext_cases.py`/`kyc_policy.py` rather than re-register them from a new module. (c) *Identity* — `ext_cases.acting_user(authorization, claimed)` prefers `ext_auth.current_user`; slice 4 must enforce tiers through `rbac` (kept in sync from the `users` table by `ext_cases.sync_rbac()`), never from the request body alone. (d) *Memo version numbering (slice 3 — read this first)* — number `assessment_memos.version` **per (`case_id`, `cycle`)**, starting at 1 for each cycle, and write the `cycle` column. Slice 3's acceptance asserts version 1 then version 2 for `ACC-HIGH-001`; on a cumulative second run in one process slice 2 re-POSTs that reference first, so the case is at cycle 2 and naive per-case numbering would yield 3 and 4 and fail every memo check. (e) *Decision idempotency* — slice 4's "second decision on the same case → 409" must key off **an existing `approvals` row for (`case_id`, `cycle`)**, not off `cases.status`. Intake deliberately stays permissive: a resubmission reopens a decided case as a new cycle rather than returning an error, because refusing it would break a cumulative acceptance re-run in a single process (slice 2 re-POSTs `ACC-HIGH-001` after slice 4 has approved it). Keying on (case_id, cycle) gives the right answer in both a single run and a repeated one. (f) *Decisions must stamp the cycle* — slice 4 must call `ext_cases.stamp_cycle(case_id, decision=…, decided_at=…, decided_by_user_id=…, decided_by_role=…)` when it records a decision; the `case_cycles` snapshot carries those columns and slice 6's `/cases/{ref}/reproduction` reads them, so without the call a decided-then-resubmitted cycle reproduces with a stale `"ready"`/`"returned"` outcome. (g) *Score/SLA on resubmission* — the score and SLA fields are cleared at the start of every cycle and only rewritten on the complete path, so slice 5's evaluator must skip cases with no `sla_due_timestamp` rather than assume one exists.


- **Slice 2 — Deterministic risk scoring and banding** (`deterministic-risk-scoring`; REQ-016…REQ-028, REQ-071, REQ-091). Adds the standalone read/verify surface around the risk engine that slice 1 already computes on intake — the scoring itself remains where it was built: `ext_cases.compute_risk_score_from_matrix`, the `case-intake-and-risk-scoring` workflow's registered handler, `kyc_policy.score_factors` (five weighted factors — jurisdiction .30, entity structure .25, industry .20, sanctions .15, expected activity .10 — each 0-100 by mechanical scale with an explicit "otherwise" default, Low 0-39 / Medium 40-69 / High 70-100 bands, and a sanctions true-positive override that forces High irrespective of the total). New endpoints, all registered outside `/api/` in `backend/ext_risk.py` so the `/api/{table}` catch-all cannot shadow them and no route-ordering conflict arises with `ext_cases.py`'s `/cases/{reference}` (a distinct, more specific path template — FastAPI matches by literal segment, not prefix): `GET /risk-matrix` (the published, versioned matrix — weights, per-factor scales, band ranges plus the review cadence each band carries per REQ-023/024/025, and the override rule; added `review_cadence_months` and `score_not_editable_by_any_role` to `kyc_policy.risk_matrix_definition()` for full REQ traceability without touching the scoring math), `POST /risk/score` (runs the same pure `score_factors` function against arbitrary factors, not tied to a case — proves REQ-028's reproducibility: identical input, identical output, always), `GET /cases/{reference}/score-breakdown` (reads the current cycle's `risk_scores` row written by slice 1's handler and returns each factor's raw input, raw score, weight and contribution alongside the total and band, per REQ-091), and `POST /cases/{reference}/score` (always refuses with 403, for every role including `compliance_officer` — REQ-027 — and audits the refusal as `score_edit_refused` with the attempted value, so a coerced or careless try still leaves a record). No AI is involved anywhere in this slice (REQ-016): it is plain deterministic code calling `kyc_policy`, never `agent_runtime.respond`. UI: a live section added inside the design's existing `#screen-score` container (`frontend/risk.js`, alongside the untouched `app.js`/`cases.js`) — a case-reference lookup rendering the same weighted-factor ledger the static design mocks, a direct calculator against raw factors hitting `/risk/score`, and an "attempt to edit the score" control that demonstrates the 403 refusal; `textContent` only, `nginx.conf` given exact/prefix locations for `/risk-matrix` and `/risk/` alongside slice 1's existing entries so docker-compose can't shadow the new script or routes. Tests: `backend/tests/test_slice2_risk.py` covers the matrix, ad-hoc scoring, the override, the score-breakdown view, the 403-with-audit refusal, and replays the slice plan's acceptance checks verbatim (cumulative with slice 1's own replay in `test_slice1_cases.py` — both run in the same process, so `ACC-HIGH-001` is at cycle 2 by the time slice 3 sees it, per note (d) above).

  **Verification note.** The sandbox's `request` tool double-encodes JSON POST bodies in this environment — confirmed against the pristine, unmodified `/chat` and `POST /api/{table}` endpoints from the base scaffold, so it is a tool/environment artifact, not a regression in this slice's code. POST-body acceptance paths were therefore verified through the backend test suite (`run_tests`, which uses `TestClient` correctly in-process — 29 passed) rather than through the sandbox `request` tool; GET-only paths (`/risk-matrix`, `/checklist`, `/cases`, `/agents`, static assets) were additionally probed live and match.
